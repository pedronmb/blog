Idempotencia en APIs REST: Diseñando endpoints resilientes a redes inestables y reintentos

23 nov 2026

El usuario toca «Pagar». La API procesa el cobro, pero la conexión se corta antes de que el teléfono reciba la respuesta. La app muestra un error y vuelve a enviar POST /pagos. Si el servidor interpreta ese segundo mensaje como una operación nueva, el usuario puede terminar pagando dos veces.

Un timeout solo indica que el cliente dejó de esperar. Para recuperar el resultado sin repetir el efecto, el cliente identifica la operación con una clave estable y el servidor guarda esa clave junto con el resultado. Cuando el efecto ocurre en una pasarela externa, también hay que coordinar los reintentos con ella.

Qué se puede repetir en HTTP

Un método es idempotente si varias solicitudes idénticas tienen el mismo efecto pretendido que una sola. GET, PUT y DELETE tienen esa semántica. Por ejemplo, dos DELETE /pedidos/ped_731 pueden responder primero 204 y después 404. En ambos casos, el pedido queda ausente. Un POST necesita un contrato explícito para ofrecer esa garantía. RFC 9110, § 9.2.2.

El contrato de Idempotency-Key

Generá un UUID aleatorio antes del primer envío y guardalo con la operación pendiente si la app puede reiniciarse. Reutilizá esa clave con los mismos datos en cada reintento. Generá otra únicamente cuando el usuario inicie una operación distinta.

POST /pagos HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 64
Idempotency-Key: "df9a1b86-7a15-4ae0-9f68-3e6416aa22ad"

{"pedido_id":"ped_731","importe_centavos":129900,"moneda":"ARS"}

El ejemplo usa comillas porque el borrador de la IETF define el valor como una cadena de campos estructurados. Al llamar a una API existente, seguí el formato que documenta ese proveedor. Borrador de la IETF.

Del lado del servidor, autenticá y autorizá cada solicitud, también al recuperar una respuesta. Buscá la clave dentro del ámbito del solicitante autenticado y de la operación de API. Guardá además una huella SHA-256 de los parámetros validados que determinan el efecto, incluidos los parámetros de ruta o consulta relevantes. Usá una representación determinista para que el orden de los campos de un objeto JSON no cambie la huella.

Qué encuentra el servidorCómo responde

La clave es nueva.Reserva la clave e inicia la operación.

La operación sigue pendiente.En este diseño, el flujo asíncrono devuelve 202 Accepted con un enlace de consulta. El borrador propone 409 Conflict para solicitudes simultáneas que la API rechaza mientras procesa la primera.

Documentá cuánto tiempo se puede recuperar un resultado y qué pasa cuando vence la clave. Una política posible es retener respuestas definitivas durante 48 horas desde que la operación termina. Después de purgar la fila, una solicitud con esa clave puede iniciar una operación nueva. Si el cliente supera la ventana, puede consultar el resultado por su identificador o por una referencia de negocio antes de volver a enviar el POST.

PostgreSQL evita pedidos duplicados

Cuando todo el efecto vive en la misma base, como en POST /pedidos, guardá la reserva de la clave, el pedido y la respuesta en una sola transacción. La restricción única decide cuál solicitud adquiere la reserva, incluso cuando los reintentos llegan a instancias distintas.

CREATE TABLE solicitudes_idempotentes (
    solicitante_id   bigint NOT NULL,
    operacion        text NOT NULL,
    clave            text NOT NULL,
    huella           bytea NOT NULL,
    estado           text NOT NULL CHECK (estado IN (
        'en_proceso', 'confirmado', 'rechazado', 'incierto'
    )),
    codigo_http      smallint,
    encabezados      jsonb,
    cuerpo           bytea,
    expira_en        timestamptz,
    PRIMARY KEY (solicitante_id, operacion, clave)
);

La primera sentencia de la transacción intenta reservar la clave. Los parámetros $1 a $4 son el solicitante, la operación, la clave y la huella.

INSERT INTO solicitudes_idempotentes
    (solicitante_id, operacion, clave, huella, estado)
VALUES ($1, $2, $3, $4, 'en_proceso')
ON CONFLICT (solicitante_id, operacion, clave) DO NOTHING
RETURNING clave;
  1. Si RETURNING devuelve una fila, esta transacción tiene la reserva. Creá el pedido y actualizá la fila a confirmado con el 201 Created, el cuerpo que contiene su ID, los encabezados que correspondan y el vencimiento. Enviá la respuesta después del COMMIT.
  2. Si RETURNING queda vacío, leé la fila con un SELECT separado en READ COMMITTED. El INSERT puede esperar a que termine la transacción rival y el SELECT toma una nueva instantánea. Compará la huella y devolvé el resultado guardado o el 422. Aislamiento de transacciones en PostgreSQL.

Si el proceso cae antes del COMMIT, se revierten la reserva y el pedido. Si cae después, la siguiente solicitud con la misma clave puede recuperar el 201 y el mismo ID. En este flujo, el estado en_proceso queda dentro de la transacción. Para acotar la espera bajo concurrencia, poné un límite al bloqueo y devolvé un error transitorio si se agota.

Redis acelera los reintentos

Si muchos reintentos consultan la misma clave, usá Redis como caché distribuida de resultados definitivos ya guardados en la base. La entrada incluye el ámbito del solicitante, la operación y la clave en su identificador, y guarda la huella junto con la respuesta. Aplicá la misma autorización antes de responder desde la caché.

  1. Consultá Redis con GET. Si hay una entrada vigente, compará la huella y devolvé la respuesta guardada o el 422 correspondiente.
  2. Ante un fallo de Redis o una entrada ausente o vencida, ejecutá el flujo de PostgreSQL. Así, todas las instancias siguen sujetas a la misma reserva.
  3. Después del COMMIT, poblá la caché con SET clave valor EX segundos. Limitá ese TTL al tiempo restante de la fila en la base. Ante un desalojo por presión de memoria, la siguiente lectura puede reconstruir la entrada. Comando SET · Desalojo de claves en Redis.

Un SET ... NX EX puede coordinar trabajo durante un plazo. Si ese plazo vence mientras la primera instancia todavía opera, una segunda puede adquirir la clave. La restricción y la transacción de PostgreSQL sostienen la garantía del pedido aunque Redis pierda esa reserva temporal. Bloqueos distribuidos en Redis.

Los cobros requieren un estado recuperable

La pasarela puede cobrar y perder su respuesta antes de que tu API guarde el resultado. Un ROLLBACK en tu base deja intacto ese cobro. Si tras el timeout otro proceso inicia un cobro con una clave nueva, podría duplicarlo.

  1. Registrá la intención antes de llamar a la pasarela. En una transacción local, reservá la clave, creá el pago en_proceso con un ID propio y persistí la clave estable que enviarás a la pasarela para esa operación. Si un trabajador ejecuta el cobro, guardá también su tarea en una outbox en esa transacción. La API puede responder 202 con Location: /pagos/{id}. Patrón Outbox.
  2. Persistí el desenlace que comunica la pasarela. Si confirma el cobro, registrá confirmado y la referencia externa. Si confirma un rechazo definitivo, registrá rechazado. En ambos casos actualizá el pago y guardá la respuesta definitiva en una sola transacción. Si hay un timeout o una caída después de enviar la solicitud, tratá el resultado como incierto, incluso si la fila sigue mostrando en_proceso porque el trabajador cayó antes de actualizarla.
  3. Conciliá las operaciones pendientes. Consultá el objeto de la pasarela por su ID o por una referencia de comercio si el proveedor lo permite. También podés aplicar sus webhooks verificados, deduplicando los eventos y evitando que uno tardío revierta un estado terminal. Reintentá la llamada externa con la misma clave y los mismos parámetros solo dentro de la garantía documentada por la pasarela. Si vence esa ventana y el desenlace sigue incierto, mantené el caso pendiente de conciliación. Claves y retención en Stripe · Resultados inciertos en Stripe.

Conservá expira_en en NULL mientras el pago esté pendiente. Asigná el vencimiento del registro de idempotencia cuando haya un desenlace definitivo. Así, la limpieza de claves preserva la reserva mientras un cobro sigue incierto.

Un pago puede recibir claves distintas si el usuario paga desde dos pestañas. Si tu negocio admite un único pago por pedido, representalo con una restricción como UNIQUE (cuenta_id, pedido_id) en la tabla de pagos y hacé que ambas solicitudes reutilicen ese registro. La clave de idempotencia vincula los intentos de una solicitud. La restricción de negocio vincula todas las solicitudes que apuntan al mismo pago.

Qué reintentar y cómo probarlo

Ante cortes de red o errores transitorios documentados, reintentá con la misma clave y un límite de intentos. Usá espera exponencial con variación aleatoria (jitter) y respetá Retry-After si la API lo devuelve. Ante un 202, consultá el recurso indicado. Ante un 422 por una huella distinta, corregí el uso de la clave en el cliente.

  • Cortá la conexión después del COMMIT. El reintento debe devolver el ID original y la base debe contener un solo pedido.
  • Enviá dos solicitudes en paralelo con la misma clave. Debe haber una sola creación. Cambiá un parámetro en el siguiente envío y comprobá que responde 422.
  • Vaciá Redis o simulá que está caído. PostgreSQL debe resolver el reintento con el mismo resultado.
  • Simulá un cobro confirmado seguido de un timeout. El pago debe quedar disponible para conciliación y terminar confirmado una sola vez, incluso si se repite la tarea o el webhook.
